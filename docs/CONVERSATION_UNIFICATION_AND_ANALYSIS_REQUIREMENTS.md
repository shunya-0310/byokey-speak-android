# 会話画面統合・会話分析機能 要件定義書

更新日: 2026-07-25  
対象: BYOKey Speak Android  
状態: 実装前・要件確定案

## 1. 目的

CoachとChatsに重複している英会話機能をChatsへ統合し、画面構成とユーザーの判断負荷を減らす。

あわせて、端末内に蓄積された会話から、ユーザー自身の話し方の特徴、繰り返しやすい誤り、得意な表現、次に練習すべき項目を分析できるようにする。

本書は実装担当モデルが、追加判断を最小限にして実装へ着手できることを目的とする。

## 2. 現状確認

### 2.1 現在の共通機能

CoachとChatsは、次の機能を共通の`ConversationPane`で利用している。

- 英語、日本語、混在文の送信
- 音声入力
- Quick Assist
- 一段階Undo
- 返信の読み上げと一時停止
- 返信の日本語訳
- Web検索の明示指定
- CEFRレベルの反映
- Coach Personalities & Skillsの反映
- Vocabulary Listへの表現抽出

### 2.2 現在の主な相違点

| 項目 | Coach | Chats |
| --- | --- | --- |
| 会話管理 | 専用履歴 | 複数チャット、名前変更、ピン留め、削除 |
| 話題導線 | Topics | Daily News |
| プロンプト | 添削・日本語解説・言い換えを含む | 2〜4文の短い雑談 |
| 文脈件数 | 直近12件 | 直近10件 |
| データ上の区別 | `ChatMode.Coach` | `ChatMode.Quick` |

### 2.3 判断

Coachは独立した画面として廃止する。

ただし、コーチング機能を削除してはならない。Coachが持つTopics、添削、日本語解説、言い換え、既存履歴をChatsへ移し、すべてのチャットを「設定に応じてコーチングできる会話」として扱う。

CEFRレベルだけでは現在のChatsは長文化しない。`buildQuickChatPrompt`に「2〜4文の短文」という制約があるためである。統合時にこの固定制約を廃止し、文量と解説量をCEFRおよびSkillsから決定する。

## 3. 基本方針

1. ユーザーにCoachとChatsの使い分けを要求しない。
2. 会話の長さ、口調、添削量、説明言語はCEFRとSkillsで制御する。
3. Daily News、自由会話、Topicsの入口は異なっても、開始後は同じチャット画面を使う。
4. 既存のCoach履歴を削除しない。
5. 会話分析にユーザーのAPIを利用する場合、ユーザー操作なしに実行しない。
6. 会話、分析結果、APIキーを開発側で保管しない。

## 4. 対象画面

統合後の下部ナビゲーションは次の4項目とする。

1. Chats
2. Review
3. Progress
4. Settings

アプリ起動後の既定画面はChatsとする。

## 5. 会話画面統合要件

### FR-U01: Coachタブの廃止

- 下部ナビゲーションからCoachを削除する。
- `MainTab.Coach`への遷移処理を削除または移行する。
- 通知やTopicsからの起動先はChats内の対象チャットとする。
- Coach削除後も、設定上の「コーチの性格」「コーチスキル」という名称は維持してよい。

### FR-U02: Chatsホーム

Chatsホームには次を配置する。

- Daily News
- New Chat
- Topics
- チャット履歴

Daily NewsとTopicsから会話を開始した場合も、通常のチャット履歴として保存する。

### FR-U03: 統一会話プロンプト

`buildPrompt`と`buildQuickChatPrompt`を、原則として1つの会話プロンプトへ統合する。

統一プロンプトは次を満たす。

- CEFRに応じて語彙、構文、文量を変える。
- Skillsに応じて口調、添削量、日本語解説の有無、言い換え候補数を変える。
- C1/C2では、話題に必要であれば自然な長文を許可する。
- A1/A2では、一文を短くし、一度に扱う内容を絞る。
- 日本語解説を常時強制しない。
- 日本語解説を希望するSkillsなら、Chatsでも表示する。
- 自然な英会話を優先し、毎回の添削を強制しない。
- Daily Newsの会話では、出典URLとニュース文脈を維持する。
- Web検索の利用有無を会話本文へ不自然に表示しない。

### FR-U04: 応答の表示構造

LLM内部の応答は、可能であれば構造化する。

最低限、次の区分を扱えること。

- `reply`: 会話として表示する英語返信
- `coachNote`: 必要な場合だけ表示する短い解説
- `japaneseExplanation`: Skillsで要求された場合、または翻訳操作時に表示する日本語
- `betterOptions`: 必要な場合だけ表示する自然な言い換え
- `vocabulary`: Vocabulary Listへ保存する候補
- `sources`: Web検索またはDaily Newsの出典

構造化に失敗した場合は、通常のテキスト返信として表示し、会話を失敗扱いにしない。

### FR-U05: Topicsの移行

- 現在のCoach画面にあるTopicsをChatsホームへ移す。
- カテゴリ選択、再抽選、日本語訳、読み上げを維持する。
- Topic開始時は新しい通常チャットを作成する。
- チャットタイトルはTopicから自動生成する。

### FR-U06: 既存Coach履歴の移行

- `ChatMode.Coach`の既存レコードを削除しない。
- 初回起動時のRoom migrationで、既存Coach履歴を統合後の会話種別へ移行する。
- 移行後もメッセージ、作成日時、タイトルを維持する。
- タイトルがすべて`Coach`の場合は、最初のユーザー発話から再生成してよい。
- migrationは複数回実行されても重複変換しない。

### FR-U07: 会話種別

UI上はCoachとQuickを区別しない。

内部データとして必要なら、会話の開始元を次のように保持する。

- `FREE_CHAT`
- `TOPIC`
- `DAILY_NEWS`
- `MIGRATED_COACH`

この値はプロンプトの長短を固定するために使わない。ニュース文脈や分析表示の補助にのみ使う。

## 6. 会話分析機能

### 6.1 MVPの目的

ユーザーに次の問いへの答えを提供する。

- 自分の英語にはどのような特徴があるか。
- どの間違いを繰り返しているか。
- どの表現は自然に使えるようになったか。
- 次の会話では何を意識すればよいか。

### 6.2 MVPで分析する項目

1. 強み
2. 繰り返し発生する文法上の誤り
3. 通じるが不自然な表現
4. 語彙と表現の多様性
5. 質問への応答、話題展開、会話継続の傾向
6. Quick Assistへ頼りやすい表現
7. 過去の分析から改善した項目
8. 次に練習する項目

単発の誤入力を「癖」と断定しない。同種の事例が2回以上ある場合に、繰り返し傾向として扱う。

### 6.3 MVPの対象外

- 発音の正確性
- アクセント
- 声の抑揚
- 沈黙時間や話す速度
- 音声認識前の言い直し回数
- 医学的、心理学的な診断
- 公的なCEFR認定

音声認識後のテキストだけでは、発音や間を正確に評価できないためである。

## 7. 分析実行要件

### FR-A01: 実行方法

- Progress画面に「会話を分析」ボタンを配置する。
- MVPではユーザーの明示操作時だけLLM分析を実行する。
- バックグラウンドで自動的にユーザーのAPIを消費しない。
- 直近の分析後に十分な新規発話がない場合は、再分析の必要がないことを表示する。

### FR-A02: 最低データ量

- ユーザー発話が20件未満の場合はLLM分析を実行しない。
- 不足時は「あと何件で分析できるか」を表示する。
- 分析対象は直近30日、最大100件のユーザー発話を基本とする。
- 100件を超える場合は、新しい発話を優先する。

### FR-A03: 分析対象データ

LLMへ送信するデータを必要最小限にする。

- ユーザー発話
- 対応する直前または直後のコーチ返信
- コーチが生成した訂正箇所
- CEFR設定
- Skillsのうち、分析結果の口調に必要な部分
- 入力元
- Quick Assist利用有無

ニュース本文全体や無関係なシステムプロンプトは送信しない。

### FR-A04: 入力元の記録

今後保存するユーザーメッセージには、次の入力元を記録する。

- `TYPED`
- `VOICE`
- `QUICK_ASSIST`
- `MIXED`

既存メッセージは`UNKNOWN`として移行する。

MVPでは入力元を分析結果の補足に使う。発音評価には使わない。

### FR-A05: 分析結果

分析結果は構造化JSONで受け取る。最低限、次の情報を持つ。

```json
{
  "summary": "全体傾向の日本語要約",
  "strengths": [
    {
      "title": "強み",
      "evidence": ["ユーザーの実際の発話例"],
      "comment": "短い説明"
    }
  ],
  "recurringPatterns": [
    {
      "category": "grammar | naturalness | vocabulary | conversation",
      "title": "傾向名",
      "occurrences": 3,
      "examples": [
        {
          "original": "元の発話",
          "suggestion": "自然な表現",
          "explanationJa": "日本語解説"
        }
      ],
      "nextAction": "次回の具体的な練習"
    }
  ],
  "improvements": [],
  "nextFocus": ["次に意識する項目"],
  "practicePrompts": ["練習会話を始めるための英語または日本語の話題"]
}
```

実際のスキーマはKotlinの`@Serializable`データクラスとして固定する。

### FR-A06: 分析結果の保存

- 分析結果をRoomへ保存する。
- 分析日時、対象期間、対象発話数、利用モデルを保存する。
- 生のAPIレスポンスは保存しない。
- 過去の分析結果を時系列で参照できるようにする。
- 「学習データを削除」で分析結果も削除する。

### FR-A07: Progress画面

Progress画面に「Your English Profile」セクションを追加する。

表示項目は次とする。

- 最終分析日時
- 分析対象の発話数
- 全体要約
- 強み
- よくある傾向
- 改善した項目
- 次の練習項目
- 会話を分析
- この項目を練習

「この項目を練習」を押すと、該当する`practicePrompt`を使ってChatsに新しい会話を作成する。

### FR-A08: 分析文体

- 分析内容の事実部分は明確で簡潔にする。
- コーチの性格は、要約や励ましの口調にだけ反映してよい。
- 誤りの件数、実例、修正文を性格設定によって改変しない。
- 過剰に褒めない。
- 1回の誤りから能力全体を断定しない。

### FR-A09: 失敗時

- JSON解析失敗時は1回だけ修復または再生成を試みる。
- APIエラー時に既存の分析結果を消さない。
- エラー理由をユーザー向けの短い日本語で表示する。
- APIキー、プロンプト、生レスポンスをログへ出力しない。

## 8. ローカル分析

LLMを使わず端末内で計算できる指標は、先にローカルで集計する。

- ユーザー発話数
- 発話の平均文字数
- Vocabulary List登録語の能動使用回数
- Quick Assist利用回数
- 入力元の割合
- 同じ表現の再使用回数

これらをLLMへ渡す場合は集計値だけを使い、トークン使用量を抑える。

## 9. プライバシーとAPI利用

### FR-P01: 初回説明

初めて「会話を分析」を押したとき、次を表示する。

> 分析対象の会話テキストは、設定中のAIプロバイダーへ送信されます。BYOKey Labが会話や分析結果を受け取ることはありません。分析にはユーザー自身のAPI利用料が発生します。

同意しない場合は送信しない。

### FR-P02: 保存先

- 会話分析はユーザーが設定したAPIキーで実行する。
- 開発側のサーバーを経由しない。
- 分析結果は端末内だけに保存する。
- クラウド同期はMVP対象外とする。

## 10. データモデル案

### MessageEntity追加項目

| 項目 | 型 | 説明 |
| --- | --- | --- |
| inputSource | String | `TYPED`など。Coach/Systemは`NONE` |
| usedQuickAssist | Boolean | Quick Assist採用の有無 |

### ConversationAnalysisEntity

| 項目 | 型 | 説明 |
| --- | --- | --- |
| id | Long | 主キー |
| createdAt | Long | 分析日時 |
| periodStart | Long | 対象期間開始 |
| periodEnd | Long | 対象期間終了 |
| userMessageCount | Int | 対象発話数 |
| provider | String | 利用プロバイダー |
| model | String | 利用モデル |
| resultJson | String | 構造化分析結果 |

Roomのバージョンを更新し、既存ユーザーデータを維持するmigrationを必ず実装する。

## 11. Vocabulary Listとの連携

- 分析対象はユーザー自身の能動使用回数とする。
- Coach返信に出ただけの語と、ユーザーが使った語を区別する。
- 分析結果から「使えるようになった語」を提示できるようにする。
- 同じ語の大文字小文字、基本的な複数形、活用形を可能な範囲で統合する。
- 誤統合を避けるため、初期実装では完全一致を優先してよい。

## 12. 受入条件

### 会話統合

- 下部ナビゲーションにCoachが表示されない。
- Chatsから自由会話、Topics、Daily Newsを開始できる。
- C1/C2で話題に応じた長文応答が可能である。
- Skillsで日本語解説を指定するとChatsでも反映される。
- 既存Coach履歴がChatsから参照できる。
- 移行前後でメッセージ件数が減らない。
- Quick Assist、音声入力、Undo、翻訳、読み上げ、Web検索が維持される。

### 会話分析

- 20発話未満では分析APIを呼ばない。
- 分析ボタンを押さない限りAPIを呼ばない。
- 20発話以上で構造化分析を生成できる。
- 最低1件の強みと、該当する場合は繰り返し傾向を表示できる。
- 傾向には実際の発話例と改善例が表示される。
- 「この項目を練習」からChatsを開始できる。
- API失敗後も前回の分析結果が残る。
- 学習データ削除で分析結果も消える。
- 開発側サーバーへ会話データを送信しない。

## 13. テスト要件

### 単体テスト

- 統一プロンプトがCEFRとSkillsを含む。
- C1/C2へ短文固定ルールが入らない。
- 分析対象期間と最大100件の選定。
- 20発話未満でAPIを呼ばない。
- 構造化JSONの正常系、欠損項目、壊れたJSON。
- 入力元とQuick Assist利用状態の保存。
- migration前後のメッセージ件数一致。

### UIテスト

- Coachタブが存在しない。
- TopicsとDaily Newsから会話を開始できる。
- Progressから分析を実行できる。
- 分析中、成功、失敗、データ不足を表示できる。
- 練習ボタンから対象チャットへ遷移できる。

### 実機確認

- キーボード表示中も入力欄が隠れない。
- 長い分析結果をスクロールできる。
- ダーク、ライトの両テーマでカードの文字が読める。
- 画面回転やアプリ再起動後も分析結果が維持される。

## 14. 推奨実装順

1. データベースmigrationと既存Coach履歴の保全テスト
2. Coachタブの機能をChatsへ移動
3. 統一プロンプトと応答構造化
4. 入力元・Quick Assist利用状態の保存
5. ローカル指標の集計
6. 会話分析APIとJSON解析
7. ProgressのYour English Profile
8. 分析項目から練習チャットを開始する導線
9. 回帰テストと実機確認

## 15. 実装上の注意

- Coach画面を先に削除してから機能を移すと、Topicsや履歴を失いやすい。移行先を実装してからタブを削除する。
- `ChatMode`を即時削除するとRoomの既存値を読めなくなる。migration完了までは旧値を許容する。
- LLM分析結果だけで進捗を算出しない。件数などの客観値はローカル集計を正とする。
- 分析プロンプトへ全会話を無制限に入れない。
- 発音分析ができるように見える表現をUIへ入れない。
- ユーザーのAPIを使う処理は、分析ボタンの操作と明確に対応させる。
